# Day 16 — Output Validation and Data Exfiltration Channels

📅 18 November 2026 · 🏷️LLM security · ⏱️ ~30 min

---

## Why it matters

Days 11 to 15 worked on the way in: classifiers, sanitisers and guardrails
that try to spot an attack before the model reads it. Every one of those
entries ended the same way. Some attacks get through, so the controls that
matter most are the ones that hold *after* the model has been fooled.

Today is the way out. A prompt injection on its own only changes what the
model writes. It turns into a breach when that text is handed to something
that acts on it: a browser that fetches an image, a person who clicks a
link, a tool that sends an email, a database that runs a query. Day 12's
EchoLeak walkthrough showed that "the AI part got the attacker into the
context window. Ordinary web plumbing got the data out." That plumbing is
ordinary application code, so you can make it deterministic. It's the most
dependable layer in the stack, and
[ANALYSIS.md](../ANALYSIS.md#a-pragmatic-architecture) calls it "mandatory,
frequently forgotten" for good reason.

## The concept

### Model output is input to something else

The [OWASP Top 10 for LLM Applications](https://genai.owasp.org/llmrisk/llm052025-improper-output-handling/)
lists this as **LLM05:2025 Improper Output Handling**: "insufficient
validation, sanitization, and handling of the outputs generated by large
language models before they are passed downstream". Its key point is that
"LLM-generated content can be controlled by prompt input", so passing it on
unchecked is "similar to providing users indirect access to additional
functionality". Anyone who can get text in front of the model, including
the author of an email it retrieves, gets that indirect access.

The fix isn't new. It's the same rule web developers already follow for user
input: encode and validate for the place the text is going.

| Where the output goes | What goes wrong (OWASP LLM05 examples) | Control for that destination |
|---|---|---|
| **Browser** (chat window, rendered Markdown or HTML) | XSS. Images and previews that fetch an attacker's URL | Parse the Markdown, allow only listed elements and hosts, strict Content Security Policy |
| **Database** | SQL injection from generated queries | Parameterised queries. A read-only account if the model writes queries at all |
| **Shell or `eval`** | Remote code execution | Don't. If you must, a sandbox with no network or credentials |
| **File system** | Path traversal from generated file paths | Resolve the path and check it stays under an allowed folder |
| **Email or ticket body** | Phishing content, data sent to the wrong audience | Fixed templates, recipient allow-lists, approval that shows the full body |

OWASP's prevention list opens with "Treat the model as any other user,
adopting a zero-trust approach". The
[OWASP LLM Prompt Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/LLM_Prompt_Injection_Prevention_Cheat_Sheet.html)
adds that "output keyword filtering is not sufficient". In practice that
means scanning the reply for words like "API key" won't save you. The control
has to know where the text is going and what is allowed there.

### The exfiltration channels

Getting data *out* needs a channel. These are the ones with published,
named cases behind them:

| Channel | How data leaves | Needs a click? | Published example |
|---|---|---|---|
| **Rendered image** | Data goes into an image URL. The client fetches it to display it | No | [MITRE ATLAS AML.T0077 LLM Response Rendering](https://atlas.mitre.org/techniques/AML.T0077) lists 5 case studies, including ChatGPT, Google Bard and EchoLeak |
| **Clickable link** | Data goes into a link the user is persuaded to click | Yes | ATLAS's Slack AI case: a fake "click here to reauthenticate" link with an API key in the URL |
| **Server-side fetch** (link preview, browsing tool) | The assistant's own infrastructure requests the URL | No | Day 12's preview service. ATLAS notes that in the ZombieAgent case the requests "originated from OpenAI's infrastructure rather than the victim's endpoint or corporate network" |
| **Tool arguments** | Data goes into an email, document, ticket reply or API call that a legitimate tool sends | Sometimes an approval | [ATLAS AML.T0086 Exfiltration via AI Agent Tool Invocation](https://atlas.mitre.org/techniques/AML.T0086), rated "Realized" with 10 case studies, including a Jira Service Management case where ticket details were posted as a reply the researchers could read |
| **Many requests to an allowed host** | Each request carries one character, and the order spells out the data | No | CamoLeak (below) |

ATLAS rates AML.T0077 as "Demonstrated" (shown in realistic testing) and
AML.T0086 as "Realized" (seen in real incidents). The tool route is the one
to worry about as agents gain write access, and it's the one output filters
are worst at, because a ticket reply full of order details looks exactly
like a helpful ticket reply.

The server-side row matters for a SOC. If a vendor's cloud makes the
request, it never crosses your proxy or firewall. You only see it if the
vendor logs it and gives you the log.

### CamoLeak: a strict allow-list and data still got out

[CamoLeak](https://www.legitsecurity.com/blog/camoleak-critical-github-copilot-vulnerability-leaks-private-source-code)
is Legit Security's write-up of a GitHub Copilot Chat flaw (vendor research,
CVSS 9.6 by their account). It's worth knowing because it beat the control
most teams would reach for first.

1. **Injection.** The researcher hid instructions in a pull request
   description using an HTML comment, which GitHub doesn't display. Any user
   who asked Copilot Chat about that pull request got the hidden text in
   their context, and Copilot ran with that user's access to private
   repositories.
2. **The wall.** GitHub's Content Security Policy blocked images from
   domains GitHub doesn't own. External images in Markdown are rewritten to
   go through **Camo**, GitHub's image proxy, and each Camo URL carries a
   signature GitHub generates. The attacker can't build a new signed URL on
   the fly, so they can't put fresh data in one.
3. **The bypass.** The researcher generated, in advance, a signed Camo URL
   for every letter and symbol, each pointing at their own server, which
   returned an invisible 1x1 pixel. The injected prompt held that dictionary
   and asked Copilot to draw the target data as "ASCII art" made of those
   images. The browser fetched them in order, and the order spelled out the
   data. The write-up shows a private issue's contents and a search for
   `AWS_KEY` leaving this way.
4. **The fix.** Found in June 2025 and reported through HackerOne. GitHub "fixed it
   by disabling image rendering in Copilot Chat completely", as of 14 August
   2025.

The lesson is that no single URL carried a secret. A check that looks for
private data inside each URL sees only `/a.png`, `/b.png`. The giveaway is
the *number* of images in one answer, not their content.

### Three ways vendors have closed the image channel

| Approach | Who | What it costs |
|---|---|---|
| **Block known exfiltration methods deterministically** | Microsoft, per its [MSRC post](https://www.microsoft.com/en-us/msrc/blog/2025/07/how-microsoft-defends-against-indirect-prompt-injection-attacks), which says "a deterministic defense can guarantee that a particular attack will not succeed, even if the underlying system involves probabilistic components" | Only covers the methods you know about. EchoLeak found variants (reference-style Markdown) the filter missed |
| **Turn off image rendering** | GitHub, after CamoLeak | Answers lose images. For a coding or support assistant, few people will notice |
| **Only auto-fetch URLs already seen in public** | OpenAI, in [Keeping your data safe when an AI agent clicks a link](https://openai.com/index/ai-agent-link-safety/) (January 2026, vendor docs). An independent crawler records public URLs. A URL it hasn't seen isn't fetched automatically, and the user gets a warning instead | OpenAI states its limit plainly: it covers data leaking "through the URL itself", not whether the page is trustworthy. It also explains why it didn't rely on domain allow-lists: redirects on a trusted domain can forward to an attacker |

OpenAI's redirect point applies to Northwind too. An allow-listed domain is
only as safe as the most permissive thing on it, which is what Day 12's
preview service proved.

### What to build

These are my working rules for an in-house assistant. They're judgement, not
published guidance, but each traces back to a source above.

| Rule | Trade-off |
|---|---|
| **Parse the output into a document tree, then allow by element and host.** Never use regex on Markdown | Needs a real parser and tests. Day 12 showed regex filters miss reference-style links |
| **No external images at all.** Internal images only, by asset ID, from a store the model can't write to | Answers can't show supplier logos or external charts |
| **External links shown behind a warning, never fetched automatically** | Users get a speed bump. Too many warnings and people click through without reading, the same fatigue OpenAI describes |
| **Cap images and links per answer** | A legitimate digest may need a lot. Set the cap per app, not globally |
| **Check tool arguments against the task, not just the schema.** A ticket reply should only contain data about that ticket's customer | Needs the app to know which records belong to which ticket. That's real engineering work |
| **Approval screens show the full arguments**, including the whole body and recipients | Long bodies make approval slower. That's a fair price for a message going outside |
| **Reject rather than repair.** If output fails validation, drop the element and log it. Don't ask the model to try again with the same context | The user sometimes gets a worse answer. The alternative hands an attacker a retry loop, which is Day 15's adaptive attack |

The last row ties back to Day 15. Order Help's 22:50 output block, a phone
number in a reply that wasn't on the order, was this kind of check: compare
the output against what the task should contain, and drop what doesn't fit.

### Northwind's output validator

After Day 12, Northwind put a validator between Ask Northwind's model and
everything downstream: the chat window, the tool gateway from Day 13, and
the report runner that executes SQL for the analytics team. All fictional.
It works like this:

- It parses each answer into elements and logs one row per element type,
  host and action. Actions are `allowed`, `stripped` (removed from the
  answer), `rewritten` (shown behind a warning, not fetched) or `blocked`
  (tool call or SQL refused).
- External images are always stripped. Internal ones are allowed.
- `Tainted` is `yes` if anything with `Trust == external` (Day 12) entered
  the session before the answer was written.
- `CtxMatch` is `yes` if a URL or tool argument contains an identifier
  (order number, customer email, ticket number) that came from an *internal*
  source in the same session. It decodes Base64 and hex first. It's a cheap
  version of Day 11's canary idea.

One new tool since Day 13: `reply_ticket`, which posts a reply to a ticket
on the customer portal. The customer who raised the ticket can read it.
Ask Northwind drafts the reply and the support agent clicks **Send**, so it's
logged as user-approved.

## What to look for

1. **Count first.** **10** rows, **8** sessions, **7** users (`h.nguyen` has
   two sessions). **68** elements: **61** images, **5** links, **1** tool
   argument and **1** SQL statement. By row: **5** allowed, **2** stripped,
   **2** rewritten, **1** blocked. **4** sessions were tainted: S-601,
   S-602, S-603 and S-608.
2. **S-601 is EchoLeak's step 5, caught.** A reference-style image to an
   outside host, with an order number from `h.nguyen`'s own queue in the
   query string. The parser treated it as an image regardless of the
   Markdown style, and external images are always stripped. Nothing left.
   It still proves M-7802 is a live injection, so M-7802 needs pulling from
   the index, and anyone else who retrieved it needs checking.
3. **S-602 is the CamoLeak pattern, also caught.** Thirty-six images to one
   host in a single answer, each path a single character. `CtxMatch` is `no`
   because no single URL holds an identifier, which is exactly why a
   per-URL content check isn't enough. Stripping external images stopped
   it. If Northwind had an image proxy that fetched for allow-listed paths,
   this row would have been `allowed`.
4. **S-603 is the one that got through.** A tool call, not a render. The
   reply went to Northwind's *own* portal, so the host looks internal, but
   the audience is whoever owns T-4540, and that's a day-old account. The
   body held details of 6 orders unrelated to the ticket, and a person
   approved it. This is AML.T0086, the same shape as the Jira case: a
   legitimate tool, used as intended, posting data where the attacker can
   read it. Treat it as a likely privacy breach involving 6 customers'
   order details until someone reads the reply, and bring in the privacy
   team early to assess whether it has to be notified.
5. **The approval didn't help.** `p.dalton` approved a 1,840-character
   reply. Whether the screen showed the whole body or a one-line summary
   is the first question to ask. ANALYSIS.md's rule applies: show approvers
   the actual arguments, not the model's description of them.
6. **The noise.** S-608 is a tainted session with an external link, but the
   link was the supplier's own tracking URL from their email, with no
   internal data in it, and it was only shown behind a warning. S-605 is a
   link the user pasted. S-606 is a real output-handling catch (an UPDATE
   sent to a read-only report runner), but it's a broken request, not an
   exfiltration. S-604 is ordinary. S-607 is a big burst of images (24),
   but internal, in an untainted service session.

## Detection logic

**In plain English:**

- Look only at **tainted** sessions, where external content was in the
  context before the answer was written.
- **High:** any element where internal data appeared in a URL or tool
  argument (`CtxMatch == yes`) **and** the validator let it through.
  Something likely left.
- **Medium:** internal data appeared but the element was stripped, rewritten
  or blocked (a contained attempt), **or** one answer pointed **10 or more**
  images or links at a single host (the CamoLeak burst), whatever the
  action.
- Don't filter on whether the host is internal. S-603 went to Northwind's
  own portal, and CamoLeak went through GitHub's own proxy.

**KQL (Microsoft Sentinel / Log Analytics, over a fictional custom table):**

```kql
// Ask Northwind: data heading out through rendered output or tool arguments
// NorthwindOutputValidator_CL is a FICTIONAL custom table
let lookback = 1d;
let burstThreshold = 10;
let tainted = NorthwindOutputValidator_CL
    | where TimeGenerated > ago(lookback)
    | where Tainted == "yes";
let bursts = tainted
    | where Element in ("image", "link")
    | summarize PerHost = sum(ElementCount) by SessionId, Host
    | where PerHost >= burstThreshold
    | summarize BurstHosts = make_set(Host), MaxPerHost = max(PerHost) by SessionId;
tainted
| summarize LeakedHits    = countif(CtxMatch == "yes" and Action == "allowed"),
            ContainedHits = countif(CtxMatch == "yes" and Action != "allowed"),
            Elements      = make_set(Element),
            Hosts         = make_set(Host),
            Actions       = make_set(Action),
            UserUpn       = take_any(UserUpn),
            FirstSeen     = min(TimeGenerated)
    by SessionId
| join kind=leftouter bursts on SessionId
| where LeakedHits > 0 or ContainedHits > 0 or isnotempty(MaxPerHost)
| extend Severity = iff(LeakedHits > 0, "High", "Medium")
| project FirstSeen, SessionId, UserUpn, Severity, LeakedHits, ContainedHits,
          MaxPerHost, BurstHosts, Elements, Hosts, Actions
```

On the sample, the query returns **3 rows**: S-603 **High**, S-601
**Medium** and S-602 **Medium**. I ran the same logic in Python over the 10
rows:

```
rows 10 sessions 8 users 7 elements 68
el Counter({'link': 5, 'image': 3, 'tool_arg': 1, 'sql': 1})
act Counter({'allowed': 5, 'stripped': 2, 'rewritten': 2, 'blocked': 1})
taint sessions ['S-601', 'S-602', 'S-603', 'S-608']
S-601 h.nguyen high 0 contained 1 bursts {} -> Medium
S-602 m.ito high 0 contained 0 bursts {'px.tailspin-cdn.example': 36} -> Medium
S-603 p.dalton high 1 contained 0 bursts {} -> High
S-604 not tainted -> excluded
S-605 not tainted -> excluded
S-606 not tainted -> excluded
S-607 not tainted -> excluded
S-608 h.nguyen high 0 contained 0 bursts {} -> no alert
without taint filter, S-607 burst: 24
```

(The `el` and `act` lines count rows. The 61 images in point 1 are the sum
of `ElementCount`.)

What it excludes: S-608 (tainted, but one rewritten link with no internal
data), and S-604 to S-607 (not tainted). The last line shows why the taint
filter matters: without it, S-607's 24 internal diagrams would cross the
burst threshold and alert every night. S-606 is worth its own low-priority
report for the analytics team, since a model trying to write to the
database is a design problem even when nobody is attacking it.

**What I verified and what I didn't.** The table, its columns, `Tainted`,
`CtxMatch` and the `reply_ticket` tool are invented. `countif`, `make_set`,
`take_any`, `sum`, `isnotempty`, `iff` and `join kind=leftouter` are standard
KQL. `ElementCount` is used instead of `Count` to avoid confusion with the
`count()` function. After a left outer join, sessions with no burst have
empty `MaxPerHost`, which is why the filter uses `isnotempty`. As in earlier
entries, a table created through the older HTTP Data Collector API would
have type suffixes on its columns (`Tainted_s`, `ElementCount_d`). The query
has only been run as the Python equivalent, not in a live workspace.

**Tuning note:** 10 elements to one host per answer is my starting point,
not a published figure. A character-by-character leak of anything useful
needs far more than 10 requests, so you could raise it, but a lower number
also catches shorter leaks such as a PIN or a one-time code. Expect the
`CtxMatch` check to be the weakest part. It only matches identifiers it
knows about, it can be beaten by encodings it doesn't decode or by
splitting an identifier across elements, and it says nothing about free
text such as a customer's complaint copied into a reply. That's why the
rule leans on the validator's structural facts (element type, count, host)
as well. The biggest blind spot is S-603 without `CtxMatch`: a tool call to
an internal host, approved by a person, with no burst. The real fix there
isn't detection. It's a `reply_ticket` check that refuses to include any
order not linked to the ticket's customer, which is Day 13's taint idea
applied to one tool's arguments.
